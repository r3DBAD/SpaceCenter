## 9.4. Оптимизации

После каждой оптимизации сценарий запускался заново и ответ сравнивался с замером «до» по sha256
тела ответа (`tools/compare_lab5.py`). Во всех 12 замерах (4 сценария × 3 объема) ответы совпали.

### Оптимизация №1. С1 «Расход топлива»: пакетный запрос и индексы

Было (`services.py`, `FuelService.list_batches`):
```python
return [(b, b.remaining(self._repos.fuel.used_mass(b.id)))      # SELECT SUM … WHERE batch_id = ? на каждую партию
        for b in self._repos.fuel.list_batches(session.scope(spaceport_id))]
```
Стало:
```python
used = self._repos.fuel.used_by_batch()   # SELECT batch_id, SUM(mass_hg) FROM fuel_consumption GROUP BY batch_id
return [(b, b.remaining(used.get(b.id, Mass.zero())))
        for b in self._repos.fuel.list_batches(session.scope(spaceport_id))]
```
и в схеме `ix_consumption_batch ON fuel_consumption(batch_id)`, `ix_consumption_launch ON fuel_consumption(launch_id)`.

Обоснование: устранена проблема N+1. Было B запросов, каждый без индекса читал все C строк расхода:
O(B × C) = 2 000 × 136 557 ≈ 273 млн прочитанных строк. Стало: один проход по таблице с группировкой,
O(C + B). Индекс по `launch_id` ускоряет `loaded_by_component` и `loaded_batches` в карточке пуска и на
этапах подготовки. Результат: 10 365 → 123 мс на 50k (−99 %).

### Оптимизация №2. Все сценарии: разбор дат через `fromisoformat`

Было (`database.py`): `datetime.strptime(value, "%Y-%m-%dT%H:%M")`. Стало: `datetime.fromisoformat(value)`.

Обоснование: формат хранения — ISO 8601, его разбирает встроенная функция на C. `strptime` написан на
Python и на каждом вызове разбирает строку формата регулярным выражением и обращается к локали.
Замер timeit (100 000 вызовов): 3,41 мкс против 0,10 мкс, в 35 раз. На 50 000 пусков в С2 это
100 000 разборов: −2,3 млн вызовов функций. Результат по сценариям на 50k: С2 −28 %, С3 −45 %,
прогнозы −47 %. Тест `test_dates_roundtrip` проверяет, что обе функции дают одинаковое значение.

### Оптимизация №3. С2 «Поиск пусков»: фильтр в SQL вместо фильтра на клиенте

Было: `GET /api/launches` отдавал все пуски, фильтр по типу и статусу делала страница. Стало:
`list_launches(session, statuses, spaceport_id, vehicle_type_id)` добавляет условия в `WHERE`, индекс
`ix_launch_vehicle_status ON launch(vehicle_type_id, status)`; маршрут принимает `?vehicle_type=&status=`.
Заодно `_names` и `_pad_spaceports` берут площадки через новый `list_pads_brief` без расчета загрузки
(было 2 × 6 × 3 = 36 лишних запросов на каждый вывод расписания).

Обоснование: в память не загружаются и не проверяются строки, которые все равно будут отброшены.
На 50k из 50 000 пусков подходят 10 521, сущности создаются только для них. Поиск по индексу —
O(log N + k) вместо O(N). Результат: 1 441 → 192 мс (−87 %), пик памяти 132,5 → 28,0 МБ (−79 %).

### Оптимизация №4. С3 «Загрузка площадок»: один запрос, генератор и кэш границ периода

Было (`reports.py`, `PadLoadReport.build`):
```python
for pad in self._repos.pads.list_all():
    for occ in self._repos.launches.occupancy(pad.id):   # запрос на площадку, в нем 2 подзапроса на пуск
        start = max(occ["started"], period.start)        # period.start заново вычисляется каждый раз
        end = min(occ["finished"] or self._now, period.end)
```
Стало:
```python
acc = {}
p_start, p_end = period.start, period.end                # cached_property: вычисляется один раз
for pad_id, status, started, finished in self._repos.launches.iter_occupancy(p_start, p_end, self._spaceport):
    a = acc.setdefault(pad_id, [timedelta(), 0, 0])      # строки идут из курсора по одной
    ...
```
`iter_occupancy` — один запрос по `stage_log` с `GROUP BY launch_id` и `HAVING`, который отбрасывает пуски
вне периода; строки отдаются генератором `Database.iterate` без `fetchall`. `Period.start` и `Period.end`
стали `functools.cached_property`.

Обоснование: вместо 6 запросов с 2 × N коррелированными подзапросами — один проход по таблице.
Промежуточного списка всех 48 421 интервалов больше нет: генератор держит в памяти одну строку,
поэтому память не зависит от объема (O(1) по пускам, O(P) по площадкам). Первая версия со списком
дала время −53 %, но пик памяти вырос с 4,8 до 27,7 МБ — генератор это исправил. Результат: 798 → 316 мс
(−60 %), пик памяти 4,77 → 0,01 МБ.

Покрывающий индекс `stage_log(launch_id, status, changed_at)` проверен отдельно: запрос ускоряется
со 136 до 109 мс (−20 %). Не добавлен: индекс обновляется при каждой смене этапа на самой большой
таблице, а выигрыш 27 мс на отчете, который строят несколько раз в день.

### Оптимизация №5. Таймер прогнозов: выборка по окну в SQL

Было (`forecast.py`, `ForecastService.due`):
```python
for launch in self._repos.launches.list_all():           # все 50 000 пусков, раз в минуту
    if launch.status in FINAL_STATUSES or not self.in_lead_time(launch, now):
        continue
```
Стало:
```python
for launch in self._repos.launches.starting_between(now, now + self.LEAD_TIME):
```
`starting_between` — `WHERE window_start > ? AND window_start <= ? AND status NOT IN (…)` по индексу
`ix_launch_window`. То же сделано для вкладки «Метео» (`upcoming`).

Обоснование: вместо O(N) сущностей в Python — O(log N + k) по индексу, где k — пуски в окне (0–5).
Результат: 688 мс и 42 МБ раз в минуту → меньше 0,1 мс и 0,01 МБ.

### Оптимизации утечек

| № | Было | Стало | Обоснование |
|---|---|---|---|
| 1 | `_sessions[token] = session` навсегда | `(session, last_seen)`; сеанс истекает после 8 ч простоя (`SESSION_TTL`); при входе удаляются истекшие и лишние сеансы сотрудника, их не больше 5 (`MAX_SESSIONS_PER_USER`) | Размер ограничен: ≤ 5 × число сотрудников. | 2 | `_failed[login]` удаляется только при успехе | Когда записей больше 256 (`PURGE_AT`), удаляются те, у которых последняя ошибка старше 15 минут | Такие записи уже не влияют на блокировку, поэтому удалять их безопасно; блокировка проверена тестом |
| 3 | `Database(path)` без закрытия в тестах | У `Database` есть `__enter__`/`__exit__`; фикстура `World` закрывает соединение через `weakref.finalize`; тест миграции — `with Database(path) as db` | Соединение закрывается и при исключении |

Что сознательно не применено:
* `functools.lru_cache` для справочников (типы РН, площадки): данные меняются через интерфейс, кэш без
  сброса отдавал бы устаревшие значения, а выигрыш — один быстрый запрос на страницу;
* `collections.Counter` и `itertools.groupby`: отчеты ЛР3 уже используют `Counter` и `defaultdict`, ручного
  подсчета через `dict` в коде нет;
* `csv.DictReader` и `"".join`: CSV в системе только пишется, и уже через `csv.writer`.

## 9.5. Распараллеливание

Замеры — `tools/parallel_lab5.py`, база 50 000 пусков, время после оптимизаций.

| | Значение |
|---|---|
| `multiprocessing.Pool(4)`: создание, пустая задача, закрытие — `fork` (Linux) | 5,8 мс |
| то же — `spawn` (Windows, на нем запускают `start.bat`) | 88,1 мс |

| Сценарий | Последовательно, мс | Pool(4), пул уже создан, мс | Независимые подзадачи? | Решение |
|---|---|---|---|---|
| С1 Топливо (отчет) | 67,8 | 50,3 | По космодромам — 2 части, но это один SQL-запрос с группировкой | Не применяем: выигрыш 17,5 мс меньше стоимости `spawn` (88 мс) |
| С2 Поиск | 20,2 (SQL) | 17,8 | По диапазонам id — да | Не применяем: выигрыш 2,4 мс; оставшиеся 160 мс — сборка JSON, ее пришлось бы передавать между процессами через pickle |
| С3 Площадки | 298,0 | 157,7 | По космодромам — 2 части | Не применяем (подробно ниже) |
| Запрос прогнозов (4 пуска, служба отвечает за 0,5 с) | 2 005,4 | 502,5 (4 потока) | Да: запросы к службе не зависят друг от друга и не трогают базу | **Применяем `ThreadPoolExecutor`** |

С3. Время последовательного выполнения 298 мс. Задачи независимы только по космодромам, их два.
С прогретым пулом на Linux — 158 мс (в 1,9 раза), но на Windows создание пула `spawn` добавляет 88 мс:
158 + 88 = 246 мс, выигрыш 17 %. Держать постоянный пул нельзя без изменения архитектуры: сервер
однопоточный и работает с одним соединением SQLite, а 4 процесса с копией приложения — это
примерно вчетверо больше памяти. Каждый процесс открывает свою базу, SQLite читает ее параллельно,
но группировка все равно идет по всей таблице в каждом процессе. Вывод: распараллеливание
нецелесообразно, оставляем последовательное выполнение.

Запрос прогнозов. Задача ограничена ожиданием сети (I/O-bound), а не процессором. На время ожидания
сокета интерпретатор отпускает GIL, поэтому подходят потоки, а процессы не нужны. Подзадачи
независимы: сетевая часть (`_fetch`) не обращается к базе. Запись результатов (`_store`) осталась в
основном потоке, потому что соединение SQLite нельзя использовать из нескольких потоков. Накладные
расходы пула потоков — доли миллисекунды. Результат: 2 005 → 503 мс (в 4 раза); в худшем случае,
когда служба молчит, 4 × 30 = 120 с → 30 с. Число потоков ограничено `MAX_PARALLEL = 4`, чтобы не
перегрузить внешнюю службу. Тест `test_run_auto_fetches_in_parallel` проверяет, что 4 запроса по
0,3 с выполняются быстрее 0,9 с и результаты сохраняются в порядке стартовых окон.

## 9.8. Оценка по ИСО/МЭК 25010

**Производительность — временные характеристики.** На 50 000 пусков: С1 — 10,4 с → 0,12 с, С2 — 1,44 с →
0,18 с, С3 — 0,80 с → 0,32 с. Все пользовательские сценарии укладываются в 0,4 с. Квадратичный рост
С1 устранен: при увеличении данных в 50 раз время растет в 53 раза, а не в 1 312.

**Производительность — использование ресурсов.** Пик памяти С2 — 132,5 → 28,0 МБ, С3 — 4,8 → 0,01 МБ,
таймер прогнозов — 42 → 0,01 МБ. Число вызовов функций снизилось на 86–89 % в С2 и С3. Запросов к базе в
С1 — 2 003 → 4. Добавлено 5 индексов; их цена — дополнительная запись при вставке строк.

**Надежность — устойчивость к отказам при нагрузке.**
* Сервер однопоточный, поэтому любое долгое действие блокирует всех. Раньше таймер прогнозов каждую
  минуту занимал сервер на 0,7 с, а при недоступной службе — до 30 с на каждый пуск по очереди. Теперь
  проверка — меньше 0,1 мс, а ожидание службы — не больше 30 с на все пуски сразу.
* Пропускная способность расписания на 50k: около 0,7 запроса в секунду → около 5,5 (обратная величина
  времени С2).
* За сутки работы структуры в памяти больше не растут без предела: 8 640 → 250 сессий и 8 640 → 241
  запись о неудачных входах, прирост памяти 7,28 → 0,26 МБ. Перебор логинов больше не раздувает память.
* Соединения с базой закрываются, в том числе при исключении: 47 → 0 незакрытых в тестах.

**Вывод.** Главные потери давали не алгоритмы на Python, а работа с данными: N+1 запросов без индекса,
выборка всего с фильтрацией в памяти и медленный разбор дат. Их устранение дало −60…−99 % времени при
тех же ответах. Распараллеливание оправдано только для ожидания внешней службы; для запросов к SQLite
накладные расходы процессов на Windows больше выигрыша. Узкие места, которые остались: С3 упирается в
группировку 328 тысяч строк журнала этапов (около 140 мс в SQLite), а сборка JSON на 10 тысяч строк в С2 —
около 110 мс. Кроме того, сервер отвечает на поиск за 0,18 с, а страница рисует 10 521 строку таблицы
около 3 с: это уже слой View, его профилирование в эту работу не входило. Следующим шагом были бы
постраничная выдача расписания (на сервере и на странице) и хранимые итоги по завершенным пускам.
